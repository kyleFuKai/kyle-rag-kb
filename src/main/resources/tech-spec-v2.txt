技术规范文档 v2.0
技术委员会 2026年修订版

第一章 代码规范

1.1 提交规范

所有代码提交必须遵循以下Commit Message格式：
type(scope): message

type 类型：
- feat：新功能
- fix：Bug修复
- docs：文档修改
- refactor：重构（不影响功能）
- perf：性能优化
- test：测试相关
- chore：构建工具、依赖等变更

示例：
feat(payment): 新增微信支付接口
fix(order): 修复订单金额计算精度问题

提交前须通过本地 CI 检查（编译、单元测试、代码风格），
CI 不通过的提交禁止推送到远端。

1.2 分支策略

主要分支：
- main：生产环境代码，只接受来自 release 分支的 PR
- develop：开发主分支，日常开发在此分支基础上创建特性分支
- feature/xxx：特性开发分支，从 develop 创建，完成后 PR 到 develop
- hotfix/xxx：紧急修复分支，从 main 创建，完成后同时 PR 到 main 和 develop

代码审查规则：
- 所有 PR 至少需要 2 名同事 approve
- 禁止直接 push 到 main 和 develop 分支
- PR 发起后 24 小时内，reviewer 应给出首次审查意见

第二章 接口规范

2.1 RESTful 接口设计

接口设计遵循 RESTful 规范：
- GET：查询数据，幂等，不修改服务端状态
- POST：创建资源
- PUT：全量更新资源
- PATCH：部分更新资源
- DELETE：删除资源

URL 规范：
- 使用名词复数：/api/users, /api/orders
- 版本号在 URL 中：/api/v1/users
- 禁止使用动词：/api/getUser（错误），应为 GET /api/users/{id}

2.2 响应格式

统一响应格式：
{
  "code": 200,
  "message": "success",
  "data": {},
  "traceId": "abc123"
}

错误码规范：
- 200：成功
- 400：请求参数错误
- 401：未认证
- 403：无权限
- 404：资源不存在
- 429：请求过于频繁（限流）
- 500：服务器内部错误

2.3 API 限流策略

为保护后端服务，所有 API 接口均实施限流：
- 单用户每分钟最多100次调用
- 采用滑动窗口算法，比固定窗口更精确
- 超出限制返回 HTTP 429，响应头包含 Retry-After 字段
- AI 相关接口（大模型调用）单独限流：单用户每分钟10次

第三章 数据库规范

3.1 命名规范

- 表名：下划线分隔，复数，如 user_orders
- 字段名：下划线分隔，如 created_at
- 主键：统一命名为 id，BIGSERIAL 类型
- 时间字段：created_at, updated_at, deleted_at

3.2 必须包含的字段

所有业务表必须包含：
- id: BIGSERIAL PRIMARY KEY
- created_at: TIMESTAMP NOT NULL DEFAULT NOW()
- updated_at: TIMESTAMP NOT NULL DEFAULT NOW()
- is_deleted: BOOLEAN NOT NULL DEFAULT FALSE（软删除）

3.3 索引规范

- 每个查询高频字段必须建索引
- 软删除字段添加条件索引：WHERE is_deleted = FALSE
- 联合索引遵循最左匹配原则
- 禁止在生产环境直接 DROP INDEX（先 CONCURRENTLY 创建新索引再删旧的）

第四章 安全规范

4.1 认证鉴权

- 所有 API 必须通过 Sa-Token JWT 认证
- Token 有效期不超过 24 小时
- 敏感操作（删除、支付等）需要二次验证

4.2 SQL 注入防护

- 禁止拼接 SQL 字符串，全部使用参数化查询
- ORM 框架（JPA/MyBatis）的动态查询必须使用预编译语句
- AI 系统中模型生成的参数，必须经过白名单校验后才能传入查询

4.3 敏感数据处理

- 密码必须使用 BCrypt 加密存储
- 手机号、身份证等 PII 数据，展示时进行脱敏处理
- 禁止在日志中打印完整的敏感信息

第五章 日志与可观测性

5.1 日志规范

- 日志统一使用 Slf4j + Logback，格式中必须包含 traceId
- 异常必须记录完整堆栈，禁止只打印 e.getMessage()
- 日志级别使用约定：ERROR（影响功能的故障）/ WARN（可自动恢复的异常）/
  INFO（关键业务动作）/ DEBUG（仅开发环境开启）

5.2 链路追踪

所有对外接口和跨服务调用必须传递 traceId；
一次请求从入口到响应使用同一个 traceId，便于全链路排查。

5.3 指标与告警

- 服务必须暴露健康检查端点和 Prometheus 指标
- 核心指标（QPS、耗时 P99、错误率）接入告警，
  错误率超过 1% 持续 5 分钟触发电话告警

第六章 AI 应用规范

6.1 Prompt 管理

- Prompt 模板集中管理并纳入版本控制，禁止硬编码在业务代码里
- Prompt 变更视同代码变更，须经过评审后发布

6.2 大模型调用

- 所有模型调用必须设置超时（默认 30 秒）和失败重试，
  重试耗尽后走降级逻辑（如返回兜底话术），不得让错误直接抛给用户
- Embedding 结果必须缓存复用，相同内容不得重复计费调用

6.3 数据安全与成本

- 敏感数据（客户信息、密钥、内部文档原文）禁止发送给外部模型服务，
  发送前必须经过脱敏或白名单校验
- 每个应用须设置 Token 用量预算和用量监控，
  单接口单次调用的上下文预算在配置中显式声明

本规范自 2026年1月1日起生效，旧版（v1.4）同时废止。
规范修订须经技术委员会评审通过。
